# M0 성능 벤치마크 v2 — 사용법과 검증 결과

`bench.html` 하나로 끝나는 자립형 벤치마크다. 서버도 빌드도 필요 없다.

---

## ⚠️ v1 측정은 무효다

첫 iPhone 측정에서 모든 구간이 58.8 FPS로 나왔지만, 이건 합격이 아니라 **측정 실패**였다. 원인이 두 가지다.

**1. 부하가 화면에 도달하지 않았다.**
봇 플레이어가 리사주 곡선을 위치에 직접 대입하는 방식이라 초당 259유닛으로 움직였다. 실제 게임 캐릭터(100u/s)의 2.6배다. 봇이 적 무리를 계속 따돌려서, 적 800기를 스폰해도 화면에는 70기도 안 그려졌다. `drawCalls: 70`이 그 증거다.

**2. iOS Safari의 타이머 클램프.**
Safari는 `performance.now()` 정밀도를 1ms로 깎는다. 프레임당 0.2ms를 재려 하면 전부 0이나 1로 찍힌다. FPS 58.8도 `1000/17` — 실제로는 60fps인데 타임스탬프가 양자화된 결과다.

### v2에서 고친 것

| 항목 | v1 | v2 |
|---|---|---|
| 봇 이동 | 곡선을 위치에 대입 (259 u/s) | 목표점을 향해 **1.67 u/frame (100 u/s)** 로 이동 |
| FPS 측정 | 프레임 간격의 중앙값 | **프레임 개수 ÷ 경과 시간** (타이머 정밀도와 무관) |
| 로직/렌더 시간 | 프레임당 1회 측정 | **한 프레임에 150~60회 반복 후 나눗셈** (클램프 우회) |
| 부하 검증 | 없음 | **화면에 실제로 그려진 적 수**를 기록·판정 |
| 안정성 지표 | p10 FPS | **긴 프레임 비율(>20ms)** + 최악 프레임 |
| 최악 조건 | 없음 | **정지 모드** — 봇을 세워 적을 최대 밀집 |

부하 도달 개선폭 (세로 393×695 기준):

| 적 수 | v1 화면 적 | v2 이동 모드 | v2 정지 모드 |
|---:|---:|---:|---:|
| 400 | — | 262 | 377 |
| 800 | **70** | **508** | **777** |
| 1600 | — | 911 | 1575 |

## 실행

### PC

`bench.html`을 브라우저로 열고 **▶ 자동 벤치 실행**. 5구간(적 200~1600)을 각 4초씩 측정하고(워밍업 2초 별도) TDD §9 기준으로 판정한다.

### 모바일 — 이게 진짜 판정이다

**`serve.cmd`를 더블클릭**하면 이 PC의 IPv4 주소를 출력하고 8080 포트로 서버를 띄운다.
폰 브라우저에서 `http://<출력된 IP>:8080/bench.html` 로 접속한다.

수동으로 하려면: `npx serve -l 8080 .`

측정 체크리스트

- [ ] PC와 폰이 **같은 Wi-Fi**에 있는가
- [ ] 접속이 안 되면 Windows 방화벽에서 Node.js의 **사설 네트워크** 접근을 허용했는가
- [ ] 폰을 **세로**로 두고 측정
- [ ] 측정 중 **화면이 꺼지지 않게** 할 것 (절전 진입 시 rAF가 멈춰 수치가 왜곡된다)
- [ ] **배터리 절약 모드를 끄고**, 다른 앱·탭을 닫고 측정 (스로틀링이 걸리면 멀쩡한 렌더러를 불합격 처리하게 된다)
- [ ] 1회차는 기본 설정, 2회차는 **정지 모드 ON**으로 한 번 더

## 결과 표 읽는 법

| 열 | 의미 | 판정 |
|---|---|---|
| FPS | 프레임 개수 기반. 타이머 정밀도와 무관하게 신뢰 가능 | 모바일 45+, PC 57+ |
| 긴프레임% | 20ms를 넘긴 프레임 비율. 체감 끊김의 지표 | ≤ 5% |
| 최악ms | 가장 오래 걸린 프레임 | 참고용 (타이머 정밀도만큼 반올림됨) |
| **화면 적** | **실제로 그려진 적 수의 평균** | **여기가 낮으면 나머지 수치는 의미 없다** |
| 드로우콜 | 프레임당 `drawImage` 호출 수 | Canvas 2D의 실질 부하 |
| 로직ms | 배치 측정한 `step()` 1회 비용 | ≤ 6.0 |
| 렌더ms | 배치 측정한 `draw()` 1회 비용 | ≤ 8.0 |

**'화면 적' 열을 가장 먼저 보라.** 적 800 구간에서 이 값이 120 미만이면 판정 화면에 "부하 미도달" 경고가 뜬다. 그 측정은 버리고 정지 모드로 다시 재야 한다.

### 뷰포트 모드 — 첫 측정에서 드러난 설계 문제

iPhone 측정 데이터에 `"view": "270x480", "scale": 1`이 찍혔다. 화면은 393×695인데 캔버스는 270 CSS픽셀 폭만 차지했다는 뜻이다. **가로 31%가 빈 여백으로 버려졌다.**

TDD §2.2의 정수 배율 규칙 때문이다. `floor(min(393/270, 695/480)) = 1`이라 2배로 키울 수 없고, 1배면 화면을 못 채운다.

- **고정 모드** — TDD 원안. 모든 기기가 정확히 같은 시야를 본다 (경쟁 공정성에 유리). 대신 기기에 따라 여백이 크게 남는다.
- **채움 모드** — 정수 배율은 유지하되 내부 해상도를 화면 비율에 맞춘다 (iPhone이면 393×695@1x). 도트는 여전히 정확한 정수배라 뭉개지지 않는다. 대신 **기기마다 보이는 시야가 달라진다.**

두 모드로 각각 재보면 성능 차이(픽셀 수 2.1배)와 체감 차이를 동시에 판단할 수 있다. 이건 M0에서 결정할 사항으로 승격한다 — TDD §2.2 개정 대상.

## 헤드리스 검증 결과 (v2, 2026-08-20)

`verify2.mjs`를 Chromium(SwiftShader 소프트웨어 렌더링)으로 실행.

| 검사 | 결과 |
|---|---|
| 결정론 — 봇 이동 로직 변경 후 재확인 (같은 시드 3600스텝) | ✅ PASS |
| 다른 시드는 다른 결과 | ✅ PASS |
| **부하 도달 — 적 800에서 화면 508기** (v1은 70기) | ✅ PASS |
| 배치 측정이 0이 아닌 값을 냄 | ✅ PASS |
| 콘솔 에러 | ✅ 없음 |

### 로직 성능 (x86 컨테이너, 렌더 제외)

| 적 수 | 로직 ms/step | 예산(6ms) 대비 |
|---:|---:|---|
| 400 | 0.120 | 2.0% |
| 800 | 0.302 | 5.0% |
| 1600 | 0.706 | 11.8% |

**로직은 여전히 병목이 아니다.** 부하를 정상화한 뒤에도 적 800기에서 예산의 5%다. SoA + 공간 해시 + 오브젝트 풀 조합이 제대로 작동한다.

따라서 **M0의 합격 여부는 전적으로 렌더에 달려 있다.** 이건 좋은 소식이다. 렌더 병목에는 렌더러 교체(PixiJS/WebGL)라는 명확한 처방이 있고, TDD §3.2에서 그 전환을 위해 인터페이스를 미리 분리해뒀다. 로직이 병목이었다면 알고리즘을 다시 설계해야 했다.

**헤드리스 FPS와 렌더 절대치는 측정하지 않았다.** SwiftShader 소프트웨어 렌더링이 실제 GPU를 대표하지 못하기 때문이다. 렌더 판정은 실기에서만 유효하다.
