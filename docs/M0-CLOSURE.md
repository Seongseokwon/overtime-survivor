**핵심 결론: 로직은 병목이 아니다.** 부하를 정상화한 뒤에도 예산의 5%다.

## 2. 검증되지 않은 것 ⚠️

| 항목 | 상태 | 이유 |
|---|---|---|
| **중급 안드로이드 렌더 성능** | ❌ 미검증 | 테스트 기기 없음 |
| Canvas 2D 드로우콜 한계 (저사양 GPU) | ❌ 미검증 | 상동 |
| 뷰포트 모드 결정 (고정 vs 채움) | ⏸ 보류 | 성능 데이터가 결정에 개입하므로 함께 보류 |

**iPhone 측정은 하한을 보장하지 않는다.** A 시리즈 GPU는 중급 안드로이드(갤럭시 A 계열 등)보다 3~5배 빠르다. 여기서 60fps가 나온다는 사실은 "저사양에서도 된다"의 근거가 되지 못한다.

## 3. 이 리스크가 실현되면 무슨 일이 벌어지는가

M5(모바일 & 폴리시)에서 실기를 처음 만졌는데 성능이 미달이면:

- **최선의 경우** — 렌더러만 교체하면 된다. TDD §3.2의 `Renderer` 인터페이스 덕에 `game/systems`와 `game/core`는 손대지 않는다. 추정 비용 **1.5~2주**.
- **최악의 경우** — 렌더러를 바꿔도 부족해 콘텐츠 밀도(동시 적 수)를 줄여야 한다. 이건 게임 디자인 변경이라 웨이브 테이블·밸런스가 전부 흔들린다. 추정 비용 **3주+**.

즉 이 리스크의 기댓값은 "일정 2주 지연"이다. 프로젝트를 죽이는 종류는 아니지만, 늦게 발견할수록 비싸진다.

## 4. 완화 조치 (M1 착수와 함께 실행)

### 4.1 즉시

| # | 조치 | 비용 |
|---|---|---|
| M1 | **렌더러 인터페이스 경계를 엄격히 유지.** `game/systems`, `game/core`에서 Canvas 관련 타입이 한 줄도 새어나가지 않게 ESLint로 막는다 | 이미 설계됨 |
| M2 | **CPU 스로틀링 프록시 측정.** Chrome DevTools의 CPU 4x/6x 감속으로 저사양 CPU를 흉내낸다. GPU는 못 흉내내지만 로직 마진은 확인된다 | 10분 |
| M3 | **드로우콜 상한을 설계 제약으로 명시.** 프레임당 `drawImage` 1000회를 넘지 않도록 콘텐츠 밀도를 잡는다 | 0 |
| M4 | **CI 성능 회귀 테스트.** `pnpm bench`가 로직 시간이 임계를 넘으면 실패하게 한다 | M1에 포함 |

### 4.2 재확인 지점 — 늦어도 M3 종료 시

**M5까지 미루지 않는다.** M3(시그니처 시스템) 종료 시점이면 실제 게임 콘텐츠가 붙어 있어 측정이 훨씬 의미 있고, 문제가 나와도 M4~M5에서 흡수할 여유가 있다.

그때까지 아래 중 하나를 확보한다.

| 방법 | 비용 | 비고 |
|---|---|---|
| **중고 저가 안드로이드 구매** | 5~15만원 | 가장 확실. 갤럭시 A 계열 2~3년 전 모델이면 충분히 대표적이다. 어차피 출시 전에 필요하다 |
| 지인 기기 대여 | 0 | 30분이면 3개 모드 측정 가능. `serve.cmd` + URL만 있으면 된다 |
| 클라우드 디바이스 팜 | 무료 체험 있음 | BrowserStack 등. 다만 실기보다 성능이 부정확할 수 있다 |

> 개인적으로는 **중고 기기 구매**를 권한다. 출시 전 QA에서 반드시 필요하고, 15만원이 "2주 일정 지연 리스크"의 보험료라면 싸다.

## 5. 결정

**M1 착수를 승인한다.** 근거는 다음 셋이다.

1. 검증되지 않은 것이 **렌더 하나로 좁혀졌다.** 로직·결정론·아키텍처는 전부 확인됐다.
2. 그 하나에 **명확한 처방이 이미 준비돼 있다.** 렌더러 인터페이스 분리는 설계에 반영 완료.
3. 지금 기기가 없어 멈추는 비용이, 나중에 교체하는 비용보다 크다. M1~M2는 렌더러와 무관한 작업(결정론 코어, ECS, 콘텐츠 스키마)이 대부분이다.

**단, §4.2의 재확인을 M3 종료 조건에 넣는다.** 실기 측정 없이 M4(백엔드)로 넘어가지 않는다.
